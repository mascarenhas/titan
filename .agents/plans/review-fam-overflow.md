# PR #79 review: automatic FAM extent overflow

## Conclusion

The review finding is correct.  At `f274b9d`, an inferred/by-value direct local
such as

```titan
local packet = c.ffi_packet.new(4611686018427387904)
```

gets an `automatic_fam` plan in `checker._plan_c_allocation`.  In
`coder._codeautomaticallocationdecl` its backing bound is computed as a C
`size_t` constant expression:

```c
offsetof(ffi_packet, items) +
    (size_t)4611686018427387904 * sizeof(int)
```

On the ordinary LP64 layout (`offsetof == 4`, `sizeof(int) == 4`) the
multiplication wraps to zero, the generated byte array has only four bytes, but
`_c_fam_access.count` remains `4611686018427387904`.  Element zero therefore
passes Titan's logical bounds check and addresses storage beyond the generated
backing.  Copies and longjmp spills also trust the too-small backing extent.
This is a compiler correctness bug, not a need to distrust Titan source or C
headers.

The simplest sound fix with a Titan-quality diagnostic is to reject only an
automatic FAM plan whose *exact configured-target* extent cannot be represented
by `size_t`.  Do that in the checker by reusing the existing compile-only
`cprobe` declaration-compatibility machinery and its compile-time array-bound
predicate pattern.  No target-layout calculator, arbitrary count cap, runtime
stack policy, heap fallback, ABI change, or redundant coder hardening is needed.

## Supported trust model and invariant

Titan source, imported headers, the configured compiler, and injected probe
service are trusted inputs in the current model.  We should not try to defend
against a malicious header, impose a guessed "safe" stack size, or turn a large
automatic object into an owner behind the user's back.  Ordinary C may still
reject a mathematically representable but impractically large automatic object,
and a trusted program can still exhaust its stack.

The compiler-owned invariant is narrower and mandatory:

> Whenever the checker records `storage == "automatic_fam"`, the generated
> byte backing must represent the same literal element count retained for `#`
> and bounds checks; compiler-generated unsigned extent arithmetic must never
> wrap to a smaller object.

Rejecting only arithmetic overflow preserves that invariant without inventing a
resource policy.  A valid but enormous extent may proceed to the real C compile,
which remains authoritative for implementation object-size limits.

## Exact target predicate

For a complete `struct T` ending in `E field[]`, the emitted extent is

```text
max(sizeof(T), offsetof(T, field) + count * sizeof(E))
```

`sizeof(T)` is already a valid `size_t`.  It is therefore sufficient and exact
to prove the second operand fits.  For the nonnegative literal counts which can
select `automatic_fam`, use the overflow-free condition

```c
COUNT <= (((size_t)-1 - offsetof(T, field)) / sizeof(E))
```

where `((size_t)-1)` is `SIZE_MAX`.  Important details:

* Subtract before multiplying.  `offsetof` has type `size_t` and cannot exceed
  `SIZE_MAX`, so the subtraction cannot underflow.
* A valid complete C object element has `sizeof(E) >= 1`, so division is safe.
* Do **not** cast `COUNT` to `size_t` before this comparison.  On a target whose
  `size_t` is narrower than `lua_Integer`, that cast could itself wrap and make
  an out-of-range count look small.  The nonnegative decimal Titan integer
  literal and the unsigned `size_t` quotient compare correctly under C's usual
  arithmetic conversions on the supported ordinary C integer types.
* Once the comparison succeeds, it also proves the cast in the existing coder
  is lossless, the multiplication is at most `SIZE_MAX - offsetof`, and the
  addition cannot wrap.  The coder's existing `max(sizeof(T), ...)` expression
  is then safe without changing valid generated C.
* Prefer `((size_t)-1)` in the probe over spelling `SIZE_MAX`.  `cpreamble`
  already includes `<stddef.h>` for `size_t`/`offsetof`, but deliberately does
  not add `<stdint.h>`.  Adding another fixed-prefix header merely for
  `SIZE_MAX` would change the macro environment seen by every foreign header.
  The user-facing diagnostic may still correctly call the limit `SIZE_MAX`.

On the review layout the largest fitting count is

```text
floor((18446744073709551615 - 4) / 4)
    = 4611686018427387902
```

so `4611686018427387902` fits, `4611686018427387903` is the first overflow, and
the reported `4611686018427387904` must be rejected.  This also shows why a
generic "large literal" threshold would be wrong: a byte FAM with a small
offset can accept much larger counts than a wider element type.

## Recommended implementation

### 1. Checker: validate only the selected automatic FAM plan

Put a small helper near `_c_flexible_array_member`,
`_allocation_integer_literal`, and `_plan_c_allocation` in
`titan-compiler/checker.lua`.  Call it only after all of these are established:

* the allocation really selected `automatic_fam` (not an explicit owner,
  hidden-owner pointer, dynamic count, or non-direct expression);
* the payload is a visible complete eligible struct;
* `fam_field` is the marked FAM field; and
* `fam_count_literal` is the exact nonnegative integer stored in the plan.

Leave the intended `automatic_fam` annotations in place even when reporting an
error so error recovery does not infer a different owner type and emit a
secondary sink mismatch.  The error list already prevents code generation.

Use `checker._probe_for_c_types(st, { payload, element })`, not a host-side
`sizeof` guess.  That helper supplies the same configured compiler, C99/target
flags, fixed prefix, ordered direct headers, and rendered-origin supplemental
headers as generated C.  `st.c_profile` alone is insufficient: it knows
`size_t` and primitive traits, but not arbitrary aggregate padding,
`offsetof(T, field)`, or `sizeof(E)` when `E` is a typedef/array/aggregate.
Executing a probe is also wrong because cross-target objects need not run on the
host.

### 2. Reuse the existing C99 negative-array predicate probe

There is no need for a new target-layout subsystem or object-file value
extractor.  The checker already uses this exact technique for an enumerator
range predicate around `checker.lua:338-345`: make a synthetic `Type.CArray`
whose symbolic bound is `predicate ? 1 : -1`, then ask the module probe to
compile two identical declarations with
`validate_declaration_compatibility` (or the one-element plural form).

Render `T` and `E` with the shared `cdeclarator` renderer; do not use
`types.tostring` as C syntax.  Conceptually the candidate is:

```c
extern char titan_probe[
    (COUNT <= ((((size_t)-1) - offsetof(T, field)) / sizeof(E)))
        ? 1 : -1
];
```

The production cprobe baseline has already established that the ordered header
context compiles.  A true predicate gives a one-element array; a false predicate
gives the required C99 diagnostic for a negative array bound.  The existing
cprobe result cache automatically keys the exact rendered declaration together
with header context, toolchain flags, and target-profile identity.  Repeated
identical `(T, field, count)` checks are therefore free after the first result.

The minimal implementation can build this sentinel in the checker using the
shared `cdeclarator` and the existing compatibility API; that changes no
`cprobe.lua` code.  If maintainers prefer to keep all rendering out of the
checker, a very small `ModuleContext:validate_fam_extent(T, field, E, count)`
wrapper may build the same sentinel inside `cprobe.lua`, but it should internally
reuse the existing baseline/cache/candidate machinery rather than duplicate it.
A general constant-expression AST or a new Type tag would be an unnecessary
epicycle.

### 3. Diagnostics

Treat only a completed candidate compiler rejection as the semantic overflow
answer.  A missing/closed probe, rendering failure, compiler spawn/interruption,
workspace failure, or cleanup failure must fail closed but retain its distinct
infrastructure diagnostic.

Suggested semantic diagnostic at the allocation call location:

```text
automatic C allocation extent for flexible-array field
'ffi_packet.items' with count 4611686018427387904 exceeds SIZE_MAX
on the configured target
```

A concise one-line spelling is preferable in the implementation.  It should
name the C type/field, exact decimal count, `SIZE_MAX`, and configured target.
Do not append the probe's internal "negative array" compiler text to the normal
overflow error.

Suggested infrastructure form:

```text
cannot validate automatic C allocation extent for flexible-array field
'ffi_packet.items' against the configured target: <probe summary>
```

Do not misreport an unrenderable candidate or failed compiler invocation as a
large count.

### 4. Coder

No valid-path lowering change is required if the checker probe is authoritative:
`automatic_fam` now implies the existing constant expression cannot wrap.  This
matches Titan's checker-owned-plan architecture; the coder consumes the frozen
plan rather than rediscovering target semantics.

An alternative with less checker work is to emit a descriptive C99 negative-
array typedef immediately before the backing union.  It is mechanically sound,
uses the final target compiler once, and `codestat`'s `#line` attribution would
point at the Titan declaration.  It is nevertheless second-best: users receive
a generated-C constraint diagnostic rather than a Titan checker diagnostic,
and type errors are no longer all found before code generation.  Do not add both
checks merely as defense in depth; under the supported trust model one exact
authoritative check is enough.

Do not replace overflow with `sizeof(T)`, clamp the count, or silently select
owned storage.  A `sizeof(T)` prefix is conservative but not exact when the FAM
offset precedes trailing padding; clamping would preserve a false logical bound;
and owner fallback changes the inferred type/lifetime semantics.

## Edge cases to pin

* **Zero count:** accepted.  The tail term is `offsetof`; the backing remains
  `max(sizeof(T), offsetof)`, normally `sizeof(T)`.
* **`sizeof(E) == 1`:** a huge literal may still fit and must not be rejected by
  an arbitrary literal cap.  The compiler decides from the exact predicate.
* **Wider/aggregate/array element:** the actual target `sizeof(E)`, including
  typedefs and nested arrays, divides the available suffix.  Never infer it
  solely from a `Type.CInteger.bits` field.
* **Padding and alignment:** use exact `offsetof(T, field)`, not `sizeof(T)` and
  not a sum of parsed field widths.  `sizeof(T)` can include trailing padding
  after the nominal FAM offset.
* **Exact boundary:** accept `count == floor((SIZE_MAX - offset)/elem_size)`;
  reject boundary plus one.  The eventual real C compiler may separately reject
  the accepted boundary as an object too large for that implementation; that is
  not underallocation.
* **Count equal to or above `SIZE_MAX`:** on LP64, `SIZE_MAX` itself is beyond
  Titan/Lua's signed integer-literal range.  On a narrower-`size_t` target with
  a 64-bit `lua_Integer`, it is expressible and must be compared before any
  `size_t` cast.  An ordinary FAM has a positive prefix, so `count == SIZE_MAX`
  cannot fit even for one-byte elements.
* **Very large source tokens:** the lexer uses `tonumber`.  A token beyond
  `math.maxinteger` becomes `Ast.ExpFloat`, and `_allocation_integer_literal`
  does not select automatic FAM storage after unwrapping adjustments.  It goes
  through the owned/dynamic conversion path (or is rejected by type/range
  checking), so a regression test for this bug must use a real `Ast.ExpInteger`
  such as the review's `2^62`, not `18446744073709551615` on LP64.
* **Casts/adjustments:** validate `plan.fam_count_literal`, the exact count which
  the coder retains for backing/bounds provenance.  Do not re-read an unrelated
  endpoint type or evaluate the source expression in host Lua.

## Tests

The focused ownership is already clear:

* checker FAM planning/provenance is in
  `spec/checker/c_ffi_owned_types_spec.lua` (the existing
  "allocates flexible-array-member structs with count provenance" case);
* automatic object planning is also covered by
  `spec/checker/c_ffi_stack_objects_spec.lua`; and
* valid automatic/owned FAM code generation and runtime behavior are in
  `spec/coder/c_ffi_allocation_constructors_spec.lua`.

Minimum regression additions:

1. Beside the existing checker FAM case, import
   `typedef struct ffi_packet { int tag; int items[]; } ffi_packet;` and assert
   that inferred and explicitly by-value automatic forms with
   `4611686018427387904` fail with the dedicated diagnostic (type/field, decimal
   count, configured target, and `SIZE_MAX`).  This directly pins the review.
2. Keep/extend a normal accepted literal case so the successful probe branch is
   covered and its plan remains `automatic_fam` with unchanged count provenance.
   Existing `new(4)` and coder `new(3)` cases will naturally exercise it once the
   helper is installed.
3. Add a checker-only large-but-fitting case on the supported 64-bit CI targets,
   e.g. a one-byte prefix plus `unsigned char bytes[]` with `math.maxinteger`
   formatted into the source.  This proves the implementation is not an
   arbitrary "huge literal" cap.  If a host-specific exact-boundary assertion is
   considered too brittle, test the rendered predicate in the cprobe layer and
   retain only ordinary safe/overflow integration cases.
4. Assert an explicit `owned *c.ffi_packet` with the same literal does not take
   the *automatic* rejection path.  Its runtime allocation policy is separate.
5. Exercise a probe infrastructure failure and assert the "cannot validate"
   diagnostic rather than the semantic overflow diagnostic; this is useful both
   for correctness and patch coverage.

No new coder regression is needed to demonstrate rejection because codegen must
not run for the invalid source.  Retain the existing coder compile/run case for a
small automatic FAM to prove valid lowering, copying, provenance, and spills are
unchanged.  If a dedicated cprobe wrapper is added instead of reusing the generic
API directly, add focused `spec/cprobe_spec.lua` cases for accepted/rejected,
cache identity, and infrastructure failure; otherwise the mature declaration-
compatibility tests already own that machinery.

## Documentation and compatibility

This is visible source rejection and should update both manuals with the fix:

* `doc/language/c-ffi-expressions.md`, under flexible-array-member allocation:
  say that an automatic literal is checked against the configured target's
  `size_t` extent at compile time, while an owned/dynamic count is checked at
  runtime.
* `doc/implementation/foreign-functions.md` (and the short automatic-FAM link in
  `doc/implementation/c-ffi-expressions.md` if useful): record the exact quotient
  predicate and compile-only probe/plan invariant.

Valid generated layout and native signatures do not change, so this needs no
additional ABI bump beyond PR #79's existing ABI work.

## Adjacent narrow-`size_t` observation (do not silently scope-creep)

The owned runtime code currently checks

```c
(size_t)_count > (SIZE_MAX - prefix) / elem_size
```

only after rejecting negative `_count`.  That is sound on the presently tested
Linux/macOS model where nonnegative `lua_Integer` fits in 64-bit `size_t`.  If a
target with `size_t` narrower than `lua_Integer` is part of the supported target
model, the pre-check cast can wrap there too, for both ordinary owned arrays and
owned FAMs.  Such targets need a separate pre-cast representability test before
the existing quotient check.  This does not invalidate or complicate the
automatic-literal solution above; it should be confirmed against the intended
target model rather than turning this review fix into speculative hardening.
