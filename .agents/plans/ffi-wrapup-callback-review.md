# FFI wrap-up callback / generated-header review

## Findings

1. **High — source-foreign headers can silently change the consumer's checked C environment.**  `driver.lua:2546-2553` attaches the generated header of every direct source dependency, whether or not the consumer references one of its foreign functions. `coder.lua:17808-17817,18361-18377` then includes all of those headers after the consumer's direct foreign imports; a module with its own foreign functions gets the same ordering from `coder.lua:17572-17595,17641-17644`. Those dependency headers replay the producer's direct C imports, but the consumer checker/cprobe never saw that preprocessing closure. This is a same-consumer-TU check/codegen mismatch, not a request to compare or harden arbitrary cross-TU C state.

   Concrete throwaway reproduction: `consumer.h` defined `COLLIDE 1`; `provider.h` defined `COLLIDE 2`; `consumer.titan` directly imported its header, source-imported a provider that happened to define an otherwise-unused foreign function, and returned `c.COLLIDE`. The checker processed only `consumer.h`, but generated `consumer.c` included `consumer.h` then `provider.titan.h` (which included `provider.h`), and the compiled function returned **2**. A second reproduction made the producer's out-of-line foreign return typedef conditional on a consumer macro: producer C defined `int get(void)`, consumer C saw `double get(void)`, the build/link/validation all succeeded, and a source call expected to return 7 returned 0 from the ABI mismatch. The same mechanism also fails a shared, deliberately non-idempotent direct header by including it once directly and again through the dependency header.

   At minimum, generated dependency headers should be use-driven by actual source-foreign references, and every header that remains in generated C must participate in the exact consumer C preprocessing/probe context. A declaration/inline-header split may be needed to avoid replaying unrelated producer imports and macros.

2. **Low — the expanded callback bridge header is not strictly C99.** `titan-runtime/titan/ffi.h:4,32-34` includes `lstate.h` (which already typedefs `lua_State`, `TValue`, and `Udata`) and then repeats all three typedefs. Compatible typedef redefinition is a C11 feature, while Titan invokes `-std=c99`. `clang -std=c99 -pedantic-errors -I. -Ilua-5.5.1/src` rejects a TU containing only this header with three `-Wtypedef-redefinition` errors (GCC likewise rejects it with `-pedantic-errors`). Normal project flags accept the extension, so this is a portability/strict-mode issue, not an observed standard-build failure. Remove the now-redundant forward typedefs or otherwise avoid redefining them after `lstate.h`.

## Callback audit

No callback-specific correctness defect was found in the coroutine/libuv/llhttp migration:

- `titan/coroutine.titan:11-18` is mechanically equivalent to deleted `titan_coro_entry`: owner slots 0/1/2/3 are thread/module/closure/function, upvalue 2 is cast through the exact native type, and `_fn` remains `NULL`.
- The six `titan/uv` contributors preserve every deleted shim signature and slot. In particular, `titan/uv/file.titan:80-91` keeps the filesystem protocol owner-only (no eager `uv_fs_get_result`/status argument); alloc/read use slots 1/2, connection uses slot 3, and all other owners use slot 1. Each callback obtains the loop's Lua state, saves the top, pushes the **owner**, calls the exact entry, and restores the top.
- `titan/http/native.titan:84-206` preserves Parser state slot 2, callback slots 3 through 10, owner rooting, and the synchronous `int` return across stack restoration. The downstream protocols remain `HPE_OK`, `HPE_USER`, headers-complete `1`/`HPE_PAUSED`, and message-complete `HPE_PAUSED` (`native.titan:227-325`).
- `titan-runtime/titan/ffi.h:41-60` wrappers expand the intended Lua 5.5 macros and the owner push is the same stack operation as the retired `titan_pushmodule(L, owner)` path. No allocation occurs before the owner becomes stack-rooted.

Validation performed without repository edits: all 13 generated libuv declarations, all eight llhttp declarations, and the minicoro entry declaration were assigned to their upstream callback typedefs and compiled with both GCC and Clang using incompatible-function-pointer warnings as errors; the three full generated C units also passed Clang syntax checks with those warnings as errors. The current provider contains the new callbacks as hidden/local symbols and no legacy `titan_uvshim_*`, `titan_httpshim_*`, or `titan_coro_entry` symbols.
